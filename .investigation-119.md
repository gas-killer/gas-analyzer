## Investigation results — issue #119

### TL;DR

`build()` is **0.1–1.1%** of the per-request budget — basically noise.
The dominant cost depends on the analyzed tx's position in its block:

- **Early in block** (small `tx_index`): `debug_traceTransaction` dominates
  (~83%, ~8–11 s).
- **Late in block** (large `tx_index`): `replay_preceding_transactions`
  dominates (~91%, scales with `tx_index`; ~104 s for 69 preceding txs
  in the test sample).

Either way, the issue's premise — that `build()` is the bottleneck — is
incorrect. Build is two `eth_getBlockByNumber` calls plus an
`eth_chainId` probe, totaling ~100–150 ms.

### Methodology

Two examples in `crates/evmsketch/examples/`:

1. **`bench_phases.rs`** — phase-by-phase wall-time profiler using
   `Instant`. Each `build()` runs 5× cold (fresh `RootProvider` per
   iteration) for variance.
2. **`trace_rpc.rs`** — recording tower middleware logs every JSON-RPC
   request that flows through a shared `RpcClient`. Tracks method,
   params, phase tag, latency. Reports per-method totals, per-phase
   totals, and duplicate detection (same method + identical params
   issued ≥2×). All wall-time numbers below are from this recorder
   driving the full pipeline:
   `receipt → build → debug_traceTransaction → compute_state_updates → get_preceding_transactions → replay_preceding_transactions → estimate_state_changes_gas`.

   A 30 ms throttle was added to the recording layer to stay under a
   QuickNode 50 req/s limit. This inflates wall-time in RPC-heavy phases
   (~47 s of pure throttle in the late-tx run); bare numbers below
   subtract the throttle when relevant.

Run-to-run variance and provider-side caching (cold vs. warm
`debug_traceTransaction`) is real — see caveats below.

Sample: README example tx
`0x9add9d0f26bc6d867c1d6d41dda6287d9721a377cea42440250884f76d2a0fa7`,
mainnet block 24,289,218, **tx_index 69** (so 69 preceding txs in the same
block). 13 state updates extracted.

### Per-method counts (full run with replay)

| method | n | notes |
|---|---:|---|
| `debug_traceTransaction` | 1 | one big response, ~8 s cold |
| `eth_chainId` | 1 | trivially cacheable |
| `eth_getBlockByNumber` | **3** | duplicate — 2× in build, 1× in `get_preceding_transactions` |
| `eth_getTransactionReceipt` | **2** | duplicate — fetched in front_matter, then re-fetched inside `get_tx_trace` (`crates/rpc/src/lib.rs:32-38`) just to check `receipt.status()` |
| `eth_getBalance` | 266 | one per cold account during replay |
| `eth_getCode` | 266 | one per cold account during replay |
| `eth_getTransactionCount` | 266 | one per cold account during replay |
| `eth_getStorageAt` | 788 | one per cold storage slot |

**Key observation:** `SimpleRpcDb::basic_ref` issues 3 sequential RPC
calls per cold account (`crates/evmsketch/src/simple_rpc_db.rs:40-74`):
balance + nonce + code, all under `block_in_place`. For a tx that
loads 266 distinct accounts, that's 798 sequential round-trips just for
account metadata, plus 788 for storage. At ~25 ms each over HTTP
that's ~40 s of pure RPC wall-time — the actual bottleneck.

### Duplicates the recorder caught

1. **`eth_getTransactionReceipt(0x9add…)` × 2.** Once in front-matter
   (we want `block_number`, `tx_index`, `to`, `from`), once inside
   `get_tx_trace` (just to check `tx_receipt.status()`). The receipt
   should be passed through.
2. **`eth_getBlockByNumber(N)` × 2** (× 3 if you count N-1):
   - Inside `EvmSketchExecutorBuilder::build()` — 1× block N (header
     anchor) + 1× block N-1 (state_root for `BasicRpcDb`, which our
     code never uses; see below).
   - Inside `get_preceding_transactions` — 1× block N with full tx
     bodies.
   The block-N fetch is duplicated. `get_preceding_transactions` and
   `build()` could share a single fetched block.

### Same-block executor reuse: still safe (unchanged from first pass)

- `sim_env()` reads only `anchor.header()` + `chain_id` —
  immutable post-build (`crates/evmsketch/src/lib.rs:215`).
- Each estimate constructs its own `CacheDB::new(SimpleRpcDb { ... })`
  (`lib.rs:191, 322, 369`); no mutable cross-tx aliasing inside the
  executor.
- `RootProvider` is `Clone`. One executor can serve every tx analyzed
  against the same block height — `build()` cost collapses to zero
  for blocks 2..N.

### Dead-weight `get_block(N-1)` inside `build()`: still real

Confirmed by reading `sketch_builder.rs:172-196`. The N-1 block is
fetched only to seed `BasicRpcDb` with `previous_block.header.state_root`.
Our code replaces `BasicRpcDb` with our own `SimpleRpcDb` (`lib.rs:191,
322, 369`) and never reads the state_root. Skipping this saves ~50 ms.
Small absolute, ~50% of build cost — but build is already noise.

### Re-ranked follow-up tasks

The original ranking optimized for `build()`. Revised, in order of
expected reward:

| # | Task | Saving | Effort | Notes |
|---|---|---|---|---|
| 1 | **Batch `SimpleRpcDb::basic_ref` reads.** Use a single multicall or alloy's batched JSON-RPC to load balance+nonce+code+storage_slots together per account. | up to ~3× on phases 5a/5b for many-account txs | M | Right now `basic_ref` issues 3 sequential awaits inside `block_in_place`. Even a `tokio::join!` would cut latency 2-3×. A multicall contract over `eth_call` would batch many accounts in one round-trip. |
| 2 | **Switch `SimpleRpcDb` back to sp1-cc's `BasicRpcDb` (eth_getProof) where the RPC supports it.** One `getProof` returns balance, nonce, codeHash, storage slots — replaces 3+N round-trips with 1. | similar order to #1 | M | `BasicRpcDb` was avoided originally over "proof window" concerns; gate on the RPC, fall back to `SimpleRpcDb` only when proof isn't available. |
| 3 | **Concurrent in-flight reads in `replay_preceding_transactions`.** Each preceding tx's account/slot loads can be prefetched in parallel rather than blocking on each `transact_commit`'s sync DB. | up to ~5–10× on phase 5a if combined with #1/#2 | L | Architectural — revm's sync DB trait doesn't support async naturally. Could use a prefetch pass: collect access lists from preceding txs, fire a single batched warmup, then run sync replay. |
| 4 | **Same-block executor cache** at the call sites. | collapses build() to ~0 for 2..N same-block requests | S | Cache `(chain_id, block_number) -> Arc<EvmSketchExecutor>`. Almost free. |
| 5 | **Skip the redundant `eth_getTransactionReceipt`** inside `get_tx_trace` (`crates/rpc/src/lib.rs:32-38`) — pass the already-fetched receipt or its `status()` through. | ~30 ms / req | XS | Code change is local. |
| 6 | **Construct `EvmSketch` directly, skipping the dead-weight N-1 fetch.** | ~50 ms / req | S | Bypass the public builder; fields of `EvmSketch` are pub. No upstream PR needed. |
| 7 | **Cache `chain_id` across requests.** | ~16 ms / req | XS | One-time at validator startup. |

Tasks 4–7 together cut build() to effectively 0 — but build() was already
noise. The real win is tasks 1–3 on the replay+estimate path.

### Caveats

- **One tx, one provider, one block.** The bimodal pattern (trace-dominant
  early-in-block vs. replay-dominant late-in-block) is structural and
  shouldn't change with provider, but absolute numbers will. The
  README example happens to land at tx_index 69 — if the validator
  typically analyzes early-in-block txs, the trace cost framing applies;
  if late, the replay cost framing.
- **Throttling distorts wall-time in phase 5a.** With the 30 ms throttle,
  wall-time over-counts by ~47 s for the full run. Bare RPC time
  (sum of `total_ms` across all methods) was ~70 s of the recorded
  time, with throttle accounting for the rest. A real validator without
  rate-limit constraints (or a higher-tier RPC) would see roughly
  half the phase-5a wall-time.
- **`debug_traceTransaction` cost is highly cacheable on the RPC side**
  — repeated runs against the same tx hash returned in 13 ms (warm)
  vs. 8 000 ms (cold). The cold value is what a real validator sees.
- **`SimpleRpcDb` makes 3 sequential RPCs per account** because of the
  alloy `Provider::get_balance` / `get_transaction_count` / `get_code_at`
  shape. This is the actionable inefficiency; it's not inherent to the
  RPC, it's our DB adapter's structure.

### Recommendation

Reframe the latency epic. `build()` is not the bottleneck and the priority
on this issue should be lowered. The RPC-density of `replay_preceding_transactions`
+ `estimate_state_changes_gas` is the real lever, with `debug_traceTransaction`
as a secondary lever for early-in-block txs. Specifically:

- **Highest-leverage cheap win:** task #5 (drop redundant receipt fetch),
  #4 (same-block cache), #6 (skip dead-weight N-1 fetch) — each S/XS,
  add up to noticeable for any client that issues many requests.
- **Highest-leverage expensive win:** tasks #1+#2 (batch / proof-based
  account loads). These directly attack the dominant phase 5a cost.
- **Out of scope but worth flagging:** in-process revm tracing instead
  of `debug_traceTransaction` — would also collapse phase 2.

Reproducer: `RPC_URL=... cargo run --release --example trace_rpc -p gas-analyzer-evmsketch`
(append `SKIP_PRECEDING=1` to compare against the no-replay shape).
